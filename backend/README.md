# Isolated Firebase services

The same handlers support Firebase Emulator and a separately approved synthetic-data test project. They are **not connected to SkipClass**. `skip-class-slsru4` is explicitly rejected; no production rules, accounts, data, resources or deployments have been changed.

## Local run

Run `npm ci` here and in `functions`, then `npm run emulators`; run `npm run seed` in a second terminal. Java 21 is required. The pinned Node runtime is 24.12.0. The fixed launcher connects Auth, Firestore, Storage and Functions to loopback for `demo-tala-local`, imports `.emulator-data` and exports it on orderly Ctrl+C. Keep this directory, logs and synthetic account exports out of Git. The application commands are in the root README.

Only synthetic `@example.test` accounts are accepted. Booking, Evidence and learning records require verified email, current server-issued student claims and a matching UID profile. Every callable rechecks disabled/revoked sessions and current roles. Client rules also check the current protected profile role; existing ID tokens can remain valid for direct reads until refresh/expiry, so immediate production read-session revocation still needs a reviewed policy. Clients can change only their own display name; they cannot assign roles or relationships. Provisioning preserves existing nonstudent roles and family fields.

`seed` creates only local synthetic availability and never replaces occupied slots. Cloud test availability must be supplied by an authorized backend. Booking/rescheduling/cancellation use transactions, stable operation identifiers and slot/student locks. Expired bookings become `ended` and release their student lock; this records elapsed schedule time, never attendance. Evidence can reference owned non-cancelled reservations or ended bookings. Zoom joins, attendance confirmation and calendar authorization remain unavailable.

## Approved test-cloud configuration

`functions/.env.example` lists server configuration placeholders. All gates must agree: `TALA_ENVIRONMENT=test`, exact matching runtime project and `TALA_TEST_PROJECT_ID`, explicit `TALA_TEST_ENVIRONMENT_APPROVED=true`, `TALA_SYNTHETIC_ONLY=true`, a bucket belonging to that project and explicit allowed application origins. New student provisioning additionally requires a server-maintained `TALA_TEST_STUDENT_EMAILS` allowlist; existing trusted student claims are preserved. Emulator variables, credential-file overrides, Firebase CLI tokens, a demo project, mismatched projects/buckets and the SkipClass production project are rejected. Cloud services use their managed runtime identity, never a downloaded service-account key.

`test-cloud.firebase.json`, `test-cloud.firestore.rules` and `test-cloud.storage.rules` are **review artifacts**, not deployed configuration. The Storage rule's `REPLACE_WITH_APPROVED_TEST_BUCKET` deliberately denies access until the team selects its isolated bucket. Sponsor approval is still required before creating test users, deploying services/rules or provisioning billable resources. The approved project, managed identity permissions, enabled Auth provider, allowed origins and rules must be reviewed together. No deployment script is supplied.

Local collections are `tala_local_*`; approved test collections are `tala_test_*`. Both reuse `users/{Firebase UID}` rather than a second account system. Shared SkipCourse production compatibility has not been established. Existing backend relationship field names `student_id`, `principal_id`, `relationship_type` and `principal_role` are supported in the server-owned isolated relationship namespace. Legacy `users.studentIds`/`parentIds` arrays are not authorization proof and are never used to auto-link accounts. Family reads require an active server-confirmed `student_parent` relationship with recorded `family_learning_view` consent and return only UID, role and display name. This recorded consent does not authorize medical data or recordings. Parent login/dashboard access and production relationship migration are not implemented.

## Evidence and learning records

Uploads require an owner-bound intent, exact SHA-256 of the selected bytes, size/type, expiry and a synthetic-data attestation. Only immutable UTF-8 text/PDF files up to 5 MiB are accepted. The server independently checks size/type, validates the supported file format and hashes the actual bytes; this is not antivirus scanning. Submission moves the intent to `finalizing`, saves validated bytes through the GCS server API at `tala-local-evidence-private/{uid}/{uploadId}/document.txt|document.pdf` (test: `tala-test-evidence-private`), deletes client staging, then transactionally publishes Evidence metadata and increments submission count once. A permanent finalization rejection closes the intent before removing its unreferenced private object; transient errors retain private bytes for the same-intent retry. Concurrent retries do not duplicate progress or remove a committed file.

Final private objects have no Firebase download token and no client Storage read rule. Upload status is checked through the authenticated `getTalaEvidenceUploadStatus` callable, which returns only owner-scoped status/checksum/type/size. No bearer URL is returned or stored. A completed submission remains idempotently readable after its staging object is deleted or its original upload TTL expires. Authenticated Evidence file download has not been implemented; the UI currently reads metadata only.

**Remaining staging risk:** Firebase client uploads can acquire bearer download tokens before server finalization. Abandoned, invalid or expired staging files are not automatically purged; intent expiry stops further authorization but does not revoke an already issued bearer token. No scheduled cleanup resource was created. Do not upload real student, medical, recording or payment data. Reviewed quarantine/retention cleanup and file scanning are required before production use.

A current server-provisioned admin can call `publishTalaLearningRecord` to persist reviewed staff summaries for an owned student appointment after its scheduled period ends. Publication is immutable and idempotent; correction requires a separate reviewed workflow. It never confirms attendance or pretends to run AI. Students read only their published records and acknowledge existing summaries via `acknowledgeTalaOutcome`; concurrent acknowledgement increments acknowledgement count once and never changes grades, assessment counts or mastery. Meeting records, authoritative family relationships, locks and operation receipts are server-owned.

## Verification

`npm run check` and `npm run test:runtime` require no network. With all emulators running, `npm run test:integration` creates and cleans only its generated synthetic users and records. The 2026-10-20 targeted run passed 11/11 checks, including role/owner isolation, email verification, booking races/idempotency/reschedule, ended-booking lifecycle, required byte checksums, private promotion/token absence/staging deletion, failed-finalization cleanup, safe retry status, staff publication, student acknowledgement concurrency, forged family links and revoked callable sessions. These are Emulator results; no real cloud integration or Zoom/AI/payment success is claimed.

The prior cold-restart probe verified local Auth/profile/reservation/Evidence/progress persistence across export/import. This is local persistence, not cloud durability or production backup certification.

The functions runtime dependency audit reported zero advisories. Local `firebase-tools` 15.34.0 still has seven upstream advisory entries (three high, four moderate); these development-tool issues and the outstanding production policies require team review before release.
